更新日: 2026-11-27（Asia/Tokyo）

この文書は、このチャットを読めない開発者・LLM が作業を再開するための記録。確認済みの事実と、未確認・推測を分けて書く。

## 1. 最初に読む要約

- 症状: Windows で、マウスホイール（および ↑↓）で背景の黒を薄くしても、**画面上は黒いまま透けなかった**。
- 原因は 2 つ。主因は 1 つ目。
  1. **描画設定（主因）**: wgpu の既定構成では、Windows のウィンドウが「不透明」でしか合成されない。`bg_alpha` が 0 になっても黒で塗られるだけだった。
  2. **ホイールの感度**: 1 ノッチで不透明度が 50〜65% 動いていた（毎フレーム 5% 加算のため）。
- 修正（いずれも `src/main.rs`）:
  - Windows では wgpu を **DX12 + DirectComposition（`DxgiFromVisual`）** に固定する（`windows_transparent_wgpu()`）。
  - ホイールは生イベントをノッチ単位で数え、**1 ノッチ = 5%**（↑↓ キー 1 回と同じ）にする（`wheel_notches()`）。
- 画面のピクセルを実測して、透けることを確認した。単体テスト 58 件はすべて通過。このマシンのインストール版を更新済み。**ユーザーが実機で「治った」と確認した。**
- コードとこの handoff は作業ブランチ `claude/scroll-transparency-bug-d94f2a` にコミットして push した。**main へのマージ・PR 作成・リリースはしていない。**
- ユーザーが疑った OpenLogi（マウスユーティリティ）は**原因ではなかった**（§5）。
- この作業ではサブエージェントも外部 LLM も使用していない。

## 4. 原因と修正の詳細

### 4.1 描画設定（主因）

- eframe 0.34 の既定レンダラーは wgpu 29。`with_transparent(true)` を指定していても、Windows では次のようになる。
  - wgpu の自動選択では **Vulkan** が選ばれる。
  - Vulkan と、DX12 の既定スワップチェーン（`Dx12SwapchainKind::DxgiFromHwnd`）は、どちらも合成アルファ `Opaque` しか提供しない。wgpu-hal `dx12/adapter.rs` では、`SurfaceTarget::WndHandle` の場合 `vec![Opaque]` を返す。
  - egui-wgpu（`winit.rs`）は PreMultiplied / PostMultiplied が無いと `Auto` に落とし、不透明で描画する（ログ警告のみ）。StreamClock はロガーを初期化していないため、警告も見えなかった。
- 透過を扱えるのは、**DX12 で DirectComposition の visual から作るスワップチェーン（`DxgiFromVisual`）だけ**。こちらは PreMultiplied に対応する。
- 修正: `fn windows_transparent_wgpu()`（`#[cfg(windows)]`）を追加し、`NativeOptions` の `wgpu_options` に渡す。
  - `backends`: `wgpu::Backends::from_env().unwrap_or(DX12)`
  - `backend_options.dx12.presentation_system`: `DxgiFromVisual.with_env()`
  - 環境変数 `WGPU_BACKEND` と `WGPU_DX12_PRESENTATION_SYSTEM` は従来どおり優先される。DX12 が使えない機体向けの逃げ道として残した。
- macOS 側のコードは変更していない（`#[cfg(windows)]` のみ）。

### 4.2 ホイールの感度

- 旧コードは `i.smooth_scroll_delta.y` が 0 でない**フレームごとに** ±0.05 していた。egui は 1 ノッチ分を約 10 フレームに分けて流す（`wheel_state.rs` の平滑化）。そのため 1 ノッチで 50〜65% 動いていた。
- 修正: `fn wheel_notches(events, points_per_line)` を追加。`i.events` の `Event::MouseWheel` を合計する。
  - `Line` / `Page` 単位はそのまま 1.0 = 1 ノッチ（winit は WHEEL_DELTA=120 を 1.0 として渡す）。
  - `Point` 単位（トラックパッド、macOS）は、egui の `input_options.line_scroll_speed`（ネイティブでは 40pt）で割る。
  - Ctrl / Cmd 付きのホイールは egui のズーム操作なので無視する（旧コードでもこの操作は不透明度を変えていなかった）。
  - 端数は `App::wheel_notch_accum` に持ち越す。整数ノッチ分だけ ±0.05 ずつ動かす。
- `line_scroll_speed` は `ctx.input` の**外**で `ctx.options` から読む。`ctx.input` の中で Context を再ロックするとデッドロックするため（既存コメントの Esc 修正と同じ理由）。
- 単体テスト `wheel_notches_counts_events_not_frames` を追加した。1 ノッチ、OpenLogi のような連続イベント、ポイント単位、Ctrl/Cmd、無関係なイベントを確認する。

## 5. OpenLogi について（原因ではない）

- このマシンでは OpenLogi（Logitech 系マウスのユーティリティ）が常駐している。マウスイベントをフックして、ホイール 1 ノッチを複数の `MouseWheel` イベント（1〜3 行ずつ、約 70ms 以内、まれに逆符号が混じる）に分けて再送している。
- 実際のホイール操作は、OpenLogi 経由でも StreamClock に届いていた（計測ログで確認）。OpenLogi のオーバーレイには表示中のウィンドウがなく、StreamClock を覆っていなかった。
- Windows の「非アクティブウィンドウをホバーでスクロール」（`HKCU\Control Panel\Desktop\MouseWheelRouting = 2`）は有効。
- ただし、旧コードの「フレーム数で数える」処理は、この連続イベントで端から端へ振られやすかった。新コードはイベント量を合計するので影響を受けない。

## 6. 検証方法と結果

### 6.1 ホイール（合成イベント）

- テスト用ビルドの `run_native` のアプリ名を一時的に変えて起動した。こうすると eframe の保存先が分かれ、ユーザーの設定・位置を汚さない。そのウィンドウに `PostMessage(WM_MOUSEWHEEL, ±120<<16)` を送った。PostMessage は低レベルフックを通らないので、OpenLogi の影響を受けず、正確に 1 行ずつ届く。
- 修正前: 1 ノッチで不透明度が 0.5〜0.65 変化。
- 修正後: 下に 3 ノッチで 0.95 → 0.90 → 0.85、上に 3 ノッチで 1.00 に戻った（1 ノッチ = 0.05 ちょうど）。

### 6.2 画面上の透過（ピクセル実測）

- 手順（ユーザーの画面内容を見ずに判定するため、背景を自分で用意する）:
  1. Windows PowerShell 5.1 でマゼンタ一色の最前面 WinForms ウィンドウを作り、テスト用 StreamClock の下に敷く。StreamClock を `SetWindowPos(HWND_TOPMOST)` で上に戻す。
     - pwsh 7 では Add-Type 内で `System.Drawing.Bitmap` がコンパイルできなかったため、5.1 を使った。
  2. WM_MOUSEWHEEL で不透明度を 0 にする。
  3. GDI `BitBlt(SRCCOPY | CAPTUREBLT)` でウィンドウ矩形を取得し、黒とマゼンタの画素の割合を数える。
     - `Graphics.CopyFromScreen` は CAPTUREBLT を組み合わせると例外になる。
  4. スクリプトは `trap` で必ずテストプロセスを終了させる。途中で落ちると、最前面ウィンドウが残る。
- 結果（数値はウィンドウ内の画素割合。残りの約 10% は時計の数字）:

| 構成 | 不透明度 1.0 | 不透明度 0 |
|---|---|---|
| 修正前の既定（自動選択 = Vulkan） | 黒 89% | **黒 89%（変化なし）** |
| `WGPU_BACKEND=vulkan` | 黒 89% | 黒 89% |
| `WGPU_BACKEND=dx12`（HWND、wgpu 既定） | 黒 89% | 黒 89% |
| 自動選択 + `WGPU_DX12_PRESENTATION_SYSTEM=Visual` | 黒 89% | 黒 89%（Vulkan が選ばれるため効かない） |
| `WGPU_BACKEND=dx12` + `Visual` | 黒 89% | **マゼンタ 89%（透過）** |
| **修正後ビルド（環境変数なし）** | 黒 90% | **マゼンタ 90%（透過）** |

- 再ビルドせずに A/B を取りたいときは、環境変数 `WGPU_BACKEND=dx12` と `WGPU_DX12_PRESENTATION_SYSTEM=Visual` を使う。

## 8. 未確認・既知の注意点

- **OBS のウィンドウキャプチャでの見え方は未確認。** DirectComposition を使うウィンドウは、OBS の「BitBlt」方式のキャプチャでは黒くなる可能性がある。「Windows 10 (1903 以降)」方式なら取れる見込みだが、どちらも試していない。配信で使う前に確認すること。
- **DX12 が使えない GPU** では、アダプタを作れず起動に失敗する可能性がある（未検証）。その場合は環境変数 `WGPU_BACKEND=vulkan` などで起動できる。ただし背景は透けない。
- 設定パネル（`egui::Window` + `vscroll`）の上でホイールを回すと、パネルのスクロールと同時に背景の不透明度も変わる。今回の変更以前からの挙動で、今回は変えていない。
- macOS は未変更・未検証。Metal は以前から透過に対応している前提で、今回は確認していない。
